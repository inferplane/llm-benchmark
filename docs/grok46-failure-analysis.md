# Grok 4.6 호출 실패 분석

## 확인한 사실

2026-09-13 실행은 3,300개 문서를 대상으로 했습니다. 최초 실패는 101건이며,
같은 실패 키를 최대 세 차례 추가 호출한 뒤에도 55건이 남았습니다.
마지막 실패들의 측정 지연은 120.373–120.552초였고, 오류 필드는 모두 빈
문자열이었습니다. 실패는 27개 언어 방향에 걸쳐 있었으며, 원문 길이는
29–1,057자, 중앙값은 82자였습니다.

따라서 긴 문서나 특정 언어만의 문제라는 설명은 이 기록과 맞지 않습니다.
기존 Mantle 호출은 HTTPX의 연결·읽기·쓰기·풀 대기 시간을 모두 120초로
설정했습니다. 하지만 예외 클래스, 실패 단계, HTTP 상태, 요청 ID가 저장되지
않았으므로 과거에 어느 네트워크 단계가 멈췄는지, 원격 서비스 내부에서
어떤 문제가 있었는지는 소급해 확정할 수 없습니다.

## 2026-09-16 재현 확인

실패했던 입력을 모델·리전·프롬프트·생성 설정 그대로 다시 호출했습니다.
4개 사례는 읽기 제한 120초에서 완료됐고, 추가 단문 1개는 진단용 읽기 제한을
300초로 설정했지만 12초 이내에 완료됐습니다. 진단 호출은 연결 제한 15초,
쓰기·풀 제한 30초를 별도로 두어 응답 단계와 결과를 기록했습니다.
진단 코드 차이를 배제하기 위해 수정 전 `call_mantle()`도 그대로 실행했으며,
`flores-334-ko-en`과 `synthetic-ko6-ko-ar`에서 각각 2.641초와 6.893초 만에
번역 텍스트와 사용량이 반환됐습니다.

읽기 제한보다 훨씬 빨리 끝났고, 원격 서비스 지연의 과거 원인은 관측 정보가
없어 확인되지 않았습니다.

## 확인된 실행기 문제와 수정

1. **오류 정보 손실:** `str(exception)`만 저장하면 메시지가 없는 타임아웃
   예외가 빈 문자열이 됩니다. 예외 종류와 읽을 수 있는 설명을 남기고,
   가능한 HTTP 상태·실패 단계·요청 ID를 함께 기록합니다. 번역과 채점의
   오류 상세는 서로 다른 필드에 보관합니다.
2. **한 실행 안의 복구 정책 부재:** 일시적인 전송·서비스 오류를 분류하여
   제한된 지수 백오프와 지터로 재시도합니다. Grok 4.6은 처음 호출을 포함해
   최대 4회이며, 인증·잘못된 요청·콘텐츠 거절을 같은 방식으로 반복하지 않습니다.
   모든 시도는 JSONL에 남습니다.
3. **잘못된 완료 신호:** 실패가 남아도 CLI가 종료 코드 0으로 끝나던 동작을
   고칩니다. 요청된 작업이 남으면 실패 종료하고, 같은 실행을 다시 호출하면
   성공한 캐시는 유지한 채 미완료 키만 처리합니다. 빈 응답이나 완료되지 않은
   응답도 성공 캐시로 취급하지 않습니다.

모델 ID `xai.grok-4.6`, Mantle `us-west-2`, 추론 `low`, 온도 요청 0,
출력 상한 4,096토큰과 기존 120초 제한은 유지합니다. 변경된 재시도 설정은
실행 manifest와 리포트의 모델 설정에 기록합니다.

## 복구 결과의 비교 방법

9월 13일의 원본 결과와 실패 시도를 보존하고, 실패한 55개 문서만 별도 복구
실행에 기록합니다. 이후 원본의 성공 결과와 복구 결과를 `(model, id)`별로
합쳐 평가합니다. 복구 번역은 동일한 두 평가 모델로 새로 채점합니다.

여러 날짜의 부분 실행을 합친 Grok 처리량은 제공하지 않습니다. 토큰 단가
비용과 품질은 집계할 수 있지만, 실패·재시도의 미기록 과금까지 포함한 청구서
총액이라는 의미는 아닙니다. 비교 시점과 실제 실행 조건은 각 source run의
manifest를 따라야 합니다.

HTTPX의 시간 제한은 네트워크 단계별 대기 제한입니다:
https://www.python-httpx.org/advanced/timeouts/
