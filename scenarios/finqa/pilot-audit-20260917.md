# FinQA 파일럿 오류 원인 점검

대상: `finqa-nova-lite-pilot-v2-20260917`, 고정 20문항, nova-lite.
원본 응답·프롬프트·정답 스냅샷을 보존한 상태에서 검사했다.
이 점검에서는 모델 API를 추가 호출하지 않았다.

## 결론

해당 응답에 대한 자체 평가기와 공식 FinQA 평가기의 판정은 20건 모두 일치했다.
정답 2건, 실행 가능한 오답 8건, 실행 불가 10건이다.
실행 불가 10건은 표 참조를 숫자 대신 사용한 8건과 인자 개수 오류 2건이다.
공식 정답 계산식 883건도 두 평가기 모두 공식 `exe_ans`와 일치했다.
이 검사는 확인한 입력에 대한 일치 검증이며 모든 입력에서 버그가 없음을 뜻하지 않는다.

하지만 자체 프롬프트의 전역 백분율 변환 지시는 일부 공식 정답 단위와
충돌했다. 입력 표를 `table_N` 키의 배열로 제공한 설계 역시 모델이
인덱스 참조 문법을 출력하도록 유도했을 가능성이 있다. 이는 가설이며,
원본 출력만으로 인과관계를 확정할 수 없다.

평가기의 정답 계산 실행 성공만으로 평가 설계의 타당성을 검증했다고 본
이전 판단은 부족했다. 특히 10%는 수치 추론뿐 아니라 문법 준수, 문서 읽기,
데이터 주석의 단위 일관성까지 섞인 관측치다.

## 실행 불가 10건

| 원본 문항 ID | 모델 출력의 문제 | 판정 이유 |
|---|---|---|
| MRO/2009/page_139.pdf-3 | `subtract(table_2[3], table_2[1])` | 숫자 인자 대신 배열 참조 |
| AMT/2005/page_54.pdf-1 | `divide(table_5, table_4)` | 숫자 인자 대신 행 ID |
| UNP/2013/page_54.pdf-1 | `divide(table_1[3280], table_7[19686])` | 숫자 인자 대신 배열 참조 |
| MAS/2018/page_60.pdf-2 | `divide(table_5[goodwill], table_10[total])` | 숫자 인자 대신 행·열 참조 |
| FIS/2007/page_94.pdf-4 | `divide(table_2, table_6)` | 숫자 인자 대신 행 ID |
| UNP/2013/page_54.pdf-3 | `divide(table_2[automotive], table_7[total freight revenues])` | 숫자 인자 대신 행·열 참조 |
| UNP/2011/page_76.pdf-3 | `divide(table_5[325], table_9[2713])` | 숫자 인자 대신 배열 참조 |
| APD/2014/page_39.pdf-1 | `divide(table_2[88.2], table_1[450.4])` | 숫자 인자 대신 배열 참조 |
| BLL/2007/page_35.pdf-3 | `add(#0, 8310, 44.99)` | 이항 연산에 인자 3개 |
| ALLE/2016/page_43.pdf-1 | `table_min(table_1, table_2, table_3)` | 단일 행 집계 연산에 인자 3개 |

이 문법은 실행 당시 프롬프트에 허용되지 않았고 공식 평가기도 거부한다.
예를 들어 `table_1[3280]`의 괄호 내용은 열 번호인지 값인지 정의되지 않아,
이를 숫자 3280으로 자동 치환하면 모델 답변을 평가기가 임의 수정하게 된다.
따라서 자동 수선해 통과 처리하지 않았다.

## 실제 평가 설계 결함과 원본 주석 문제

**UPS/2006/page_32.pdf-3:** 모델은 `subtract(148.92, 135.02), divide(#0, 100)`을
출력했다. 실행 결과는 `0.139`, 공식 결과는 `13.9`다.
수치 차이는 정확하지만 최종 단위 변환만 다르다. 당시의 “백분율은 소수 비율로”
지시가 이 오답 판정에 영향을 줄 수 있다. 출력만으로 모델이 해당 지시 때문에
변환했다고 단정할 수는 없다.

**MAS/2018/page_35.pdf-1:** 공식 계산식은 `subtract(15.7%, 15.1%)`,
결과는 `0.006`이다. 반면 이전 프롬프트의 percentage-point 지시는
`15.7 - 15.1 = 0.6`을 유도한다. 이 문항에서 실제 모델은 `0.006`을 내 정답이었지만,
지시를 그대로 따른 다른 모델은 오답이 될 수 있다.

**PNC/2009/page_41.pdf-2:** 본문은 이익 107 million, 판매액 5.4 billion을
제시한다. 같은 단위로 환산하면 `107 / 5400 ≈ 0.0198148`, 약 1.98%로
읽기용 정답 `2%`와 부합한다. 그러나 공식 계산식은 `divide(107, 5.4)`,
`exe_ans`는 `19.81481`이다. 원본 계산식의 단위 환산 누락이다.
이 문항의 실제 모델은 다른 수치를 사용했으므로 단위 문제만으로 모델의
오답을 설명할 수는 없다.

**UNP/2013/page_54.pdf-3:** 질문은 total freight revenues 대비 자동차 매출을
묻는다. 표의 freight 합계는 20684인데 공식 계산식의 분모는 other revenues를
포함한 operating revenues 21963이다. 질문·정답 간 분모 불일치로 보인다.
전체 성능 비교 전에 사람이 확인해야 할 원본 주석 문제다.

정답 라벨을 실행 후 유리하게 수정하거나 100배 차이를 정답 처리하지 않았다.
기존 점수 2/20은 원래 규칙의 기록으로 유지한다.

## 수정 사항과 검증

프롬프트의 일괄 백분율·percentage-point 변환 지시를 제거하고, 질문에서
요구하는 단위 변환을 명시적인 계산 단계로 표현하도록 수정했다.
표 집계 연산에도 숫자만 허용하는 것으로 읽힐 수 있는 문장은
“모든 산술 연산”으로 범위를 바로잡았다.

보고서에서 모델 계산식 실행 불가, 정상 실행된 오답, 요청 실패를 구분한다.
원인별 집계와 문항별 원본 출력·실행 결과·정답을 추가했다.
기존 프롬프트에 단위 충돌 지시가 있는지 당시 스냅샷으로 확인하고 경고를 표시한다.
수정된 프롬프트를 재실행한 결과인 것처럼 과거 보고서를 표시하지 않는다.

FinQA 자체 검증, 실제 오류 형태에 대한 회귀 검증, 공식 평가기와 883개 정답 및
20개 후보 출력의 비교, HTML의 데스크톱·모바일 표시 검증을 통과했다.
프롬프트 수정의 효과는 아직 새 모델 호출로 측정하지 않았다.
원본 단위·분모 문제도 미해결이므로 현재 보고서는 규약 확인용 파일럿으로 제한한다.

공식 평가 코드는 `czyssrs/FinQA`의 `code/evaluate/evaluate.py`를 사용했다.
검사에 사용한 파일의 SHA-256:
`845cd131cab843eceff256cf6d392978cc470a7da4a80107beb56027fdca5c13`.
비교 시 감사한 네 함수(`str_to_num`, `process_row`, `eval_program`,
`program_tokenization`)만 로드했으며, 후보 문자열은 공식 DSL 처리에만 전달했다.
